OpenFinance Architecture Explainer

OpenFinance 说明书———一个可审计可复现的量化研究与风控工作台

摘要

OpenFinance 把重点放在研究过程的留存上。计划、证据包、数据集版本、因子版本、策略决策、回测结果、审批记录和风险事件都会被保存下来。聊天界面只是入口，关键在于这些对象彼此有引用，事后能顺着链路查回去。

先看结论
  • 一次请求会落成一条带 trace_id 的执行链，后续步骤都能挂回去。
  • 系统展示的是可审计的 reasoning 摘要，不会把模型的私有原始思维直接摊给用户。
  • 默认环境使用本地语料、Mock 证据和 Mock 数据，所以它更接近研究与风控工作台，还不是直接连真实市场的生产交易系统。

本文把四层分开讲：运行时事件、持久化状态、用户可见界面、后台编排逻辑。把这四层分清，OpenFinance 的运行方式就比较容易看明白。

1. 它不是陪你聊天的 AI，而是一套能落地、能追踪、能复盘的研究系统

OpenFinance 的聊天页确实长得像聊天产品，但后端并不把每句话都当成普通问答。/chat/message 会先做意图分流：是一般信息查询、研究流水线、基于上一次结果的修改、跨市场比较，还是风控控制动作。

被判定为研究型请求后，系统会创建任务、发事件、生成研究计划、准备证据、构造数据集、跑多组实验，再把最优实验和沿途工件挂回同一条链路上。前端聊天页看到的是回答卡片，任务页看到的是父子任务树，开发者模式看到的是推理步骤流，.openfinance/registry 里则留下可供事后检索的状态。

聊天回答只是最外层投影。后面那三层并行产物，才撑起了可追踪和可复盘能力。

用户看到的

聊天卡片、运行中任务条、风险快照、审批快照、任务页、证据页、因子页、报告页。

系统真正关心的

trace_id、task_id、plan_id、evidence_pack_id、dataset_version、factor_version、run_id 与对应的审计事件。

更准确的理解方式，是把 OpenFinance 看成一个把自然语言请求翻译成研究工作流的外壳。模型只是其中一环，任务编排、证据持久化、版本编号和风险门禁同样在起作用。

2. 一句话发出去之后，系统内部到底发生了什么

从运行路径看，一条消息至少要经过五次转换：先被识别成什么类型，再被绑定到哪个市场和上下文，再决定是同步回答还是异步任务，再一路产生活动事件，最后把结果挂回会话记忆与工件注册表。

先判定上下文，而不是先生成答案

聊天路由会先识别语言、市场和意图。市场解析有明确优先级：用户显式指定的市场优先，其次是消息里提到的市场，再其次是会话记忆里的 last_market，最后才回落到默认市场。这样做是为了让“再跑一次”“按当前市场继续”之类的请求有确定语义。

一般信息查询走同步路径

如果被判定为一般市场信息查询，系统会取证据、生成带引用的概括，并附上最小化 reasoning 步骤，例如“意图识别”“证据检索”“答案综合”。这条路径不会进入完整的量化实验流水线。

研究型请求被改写成父任务

如果请求是“给我一个低回撤策略并回测”这类研究任务，系统会创建父任务，立即返回会话响应，并通过 SSE 持续推送 task.created、task.progress、task.variant_started、task.variant_done、task.done 等事件。这样聊天页可以先显示“正在运行”，不必等所有实验结束。这里的 variant，可以理解成同一研究目标下的一组具体实验配置，例如不同窗口、不同因子组合或不同策略约束。

后台开始真正的研究循环

研究引擎先生成计划，再构建证据包，再准备数据集，然后对实验矩阵里的多个 variant 逐个做因子构建、策略决策、回测运行和结果比较。每个阶段都发事件，也都会留下工件。

结果不是结束，而是新的上下文起点

任务完成后，会话会记住 last_run_id、last_plan_id、last_report_id、last_dataset_version 和 last_market。这时下一句“把成本翻倍再跑一次”通常会在现有产物上继续变异，不用从头来过。

运行时事件和持久化状态不是一回事

SSE 事件来自内存事件总线，最近历史只保留一个短窗口，用来支撑实时界面；可追溯性主要落在任务注册表、审计日志、证据库、因子库、运行注册表和审批库上。实时流负责把过程送到眼前，持久化工件负责让你事后还能把过程拼回来。

如果你盯着界面看

你会看到聊天回答、运行条、任务树、证据卡片、风险快照和开发者 trace。这些都是用户可见投影。

如果你盯着系统看

你会看到另一组对象在移动：事件总线里的消息、注册表里的版本、审计日志里的动作、审批库里的状态迁移，以及回测报告中的血缘引用。

层 在 OpenFinance 里是什么 作用

3. 为什么它不会“算完就忘”：数据、计划、因子、策略和证据如何被保存下来

OpenFinance 的关键设计是：研究对象都先被编号，再被保存。只要对象有版本，后续结果就能引用它；只要引用链条完整，复盘和恢复就不是拍脑袋。

数据不是临时内存，而是可重建的数据集版本

数据集由 MockDataFactory 生成，版本号不是随机字符串，而是由 schema（字段结构）、seed（固定随机种子）和生成配置一起算出的指纹。生成后的数据集实体写到 .openfinance/data/{dataset_version}.json，同时把索引追加到 .openfinance/registry/datasets.jsonl。注册表里还会保存 lineage 和质量报告；这里的 lineage，可以理解成“它是从哪组输入和配置派生出来的血缘记录”，质量报告则会标出缺失率、回填率、异常率，以及是否引入生存者偏差。所谓生存者偏差，就是只保留“活到最后”的样本，结果把效果看得过于乐观。

计划、证据和运行结果都被正式持久化

研究计划写入 .openfinance/registry/plans.jsonl。它除了问题描述，还会收进实验矩阵、候选因子、候选策略族、约束条件，以及 orchestrator 产生的 agent 输出、reasoning 步骤和工具结果。到了这一步，plan 已经是带编排上下文的运行对象，不是静态草稿。证据包进入 .openfinance/registry/evidence.sqlite3，其中每个来源都带有可信度、时效性和评分拆解。当前仓库里，这些证据主要来自本地语料检索，再混入 Mock 新闻和 Mock 宏观适配器；可选的 WebRetriever 并没有默认启用。回测运行写入 .openfinance/registry/runs.jsonl，具体报告落在 .openfinance/data/{run_id}.json，报告里保留了 audit_trace_id、factor_versions、strategy_decision、evidence_refs、订单、成交、持仓、成本和归因。

会话记忆同样不会丢在前端本地状态里。.openfinance/registry/chat_sessions.json 会记住 last_run_id、last_plan_id、last_report_id、last_dataset_version 和 last_market；.openfinance/registry/tasks.json 则把父子任务树、进度和结果引用存下来，所以系统重启后也知道哪些任务被中断过。

因子是第一类工件，策略则主要通过运行历史保留下来

因子版本写入 .openfinance/registry/factors.sqlite3，因子工件和健康报告落在 .openfinance/artifacts/factors 下。策略没有单独的 SQLite 注册表。这也说明 OpenFinance 现在更偏向追踪一条研究实验链：策略版本主要通过回测请求和最终报告留档，没有被单独当成主数据对象管理。

4. 多个 agent 不是各说各话：它们如何分工、接力和协同

这里的 agent 不是聊天人格，更像一组被 orchestrator 顺序调度的专业视角。研究流水线默认会调用 Buffett、Soros、Simons、Dalio、Kahneman 和 Factor 六个视角。它们收到的是同一问题、同一证据包、同一市场上下文和同一约束，只是关注点不同。

共享输入

证据包、市场上下文、计划约束、研究问题、会话与任务标识、研究循环上下文。

各自差异

不同关键词、不同镜头、不同反证查询偏好。比如 Kahneman 会额外做反事实检索，Factor 更关注样本外稳定性和参数脆弱性。

它们之所以能接上，靠的是统一的输入约束和统一的输出格式。每个 agent 都必须返回严格 JSON，里面至少要包含结论、理由、证据引用、不确定性和结构化 reasoning 步骤。这样 orchestrator 才能把输出并入同一份 agent_outputs、reasoning_steps_by_agent 和 tool_results。

orchestrator 也不只是把原证据包分发出去。它会为每个 agent 构造一轮研究循环：先定义初始证据查询，再自动拼出反证查询，再把初始来源 id 和反向来源 id 都写进 research_loop。所谓“多 agent 协作”，在这里就是一个能执行的协议：每个视角都要给出看法，也都要接受反例检验。

默认工具边界收得很紧。研究流水线传给 orchestrator 的，是读取数据集版本、读取运行版本、读取市场规则和读取风险控制这四个只读工具；工具注册表里另外还预留了一个高风险的 submit_live_order，但它必须走审批，不能在研究流程里默认越权触发。agent 能查状态，但不能绕过审批去执行高风险动作。

这里的协同本质上是编排，不是自治社会

OpenFinance 没把 agent 做成彼此自由谈判的黑箱社会，而是让它们在统一任务边界内产出可比较、可审计、可回收的结构化结果。研究与风控更需要稳定接口，不需要戏剧化对话。

5. 可解释性到底解释什么：系统怎样展示过程，又怎样保留边界

OpenFinance 对 reasoning 的处理比较克制。它不会把模型原始思维全文暴露出来，也不会只给一个最终答案。系统展示的是可审计的操作摘要，也就是每一步做了什么、用了哪些证据、信心怎么变化。

被保留下来的，是结构化 reasoning trace

每个 reasoning step 都有固定字段：所属 trace、所属任务、agent 名称、步骤序号、步骤类型、标题、摘要、证据引用、置信度变化、解析错误和 prompt hash。步骤类型也被限制在少量语义明确的类别里，例如 hypothesis、evidence_use、counterevidence_use、revision、decision 和 warning。

这类表示方法的好处是，前端可以用它做实时 trace、开发者抽屉和复盘页，后台可以把它写入审计日志，trace 恢复接口也可以重新拼装回来；但它不会泄漏原始 chain-of-thought，因为 agent 提示词本身已经明确要求“只返回严格 JSON，不要包含 private chain-of-thought，只给 user-safe summaries”。

被故意保留边界的，是原始内心过程

在开发者模式里，你能看到的是 prompt_hash、解析是否出错、步骤摘要、引用到的来源，以及最终 agent 输出。这里的 prompt_hash 不是提示词全文，而是提示模板的指纹，用来标记这一步来自哪一版提示。界面保留的是可核对的外显痕迹，不会把私有中间推断整段倒出来。这个边界写在接口上，不靠文案自觉。

系统愿意公开的解释面

步骤标题、步骤摘要、证据引用、置信度变化、parse error、prompt hash、任务与风险快照、trace restore 的恢复摘要。

系统刻意不公开的部分

模型未经整理的原始私有思维、未过滤中间草稿、无法作为稳定接口的自由联想内容，以及不带证据锚点的内部推断残片。

为什么这样设计

研究和风控更关心“你凭什么得出这个结论”。至于模型脑中闪过了什么未过滤念头，既难验证，也容易泄漏不稳定甚至无意义的中间内容。

如果 agent 返回的 JSON 解析失败，系统不会把损坏输出直接塞给用户，而是打上 parse_error，再回退到安全的 reasoning 步骤模板。测试专门覆盖了这种情形，确保至少还能看到 hypothesis、decision 和带 parse_error 的 warning，不至于让界面直接空掉。

trace 恢复接口也说明，这不是一次性的 UI 技巧。它会从审计日志、运行注册表、计划注册表、证据库和聊天会话记忆里把相关对象重新装回一个上下文包；如果某些工件已经不在了，也会明确标记 partial_restore 和 missing。

系统展示的 reasoning 系统不展示的内容
步骤类型、摘要、证据引用、置信度变化、prompt hash、解析错误 原始私有 chain-of-thought 文本
可以进入 SSE、审计日志、trace 恢复、开发者模式 不能被当成稳定接口，也不会作为用户默认可见内容

6. 因子和策略不是拍脑袋来的：它们是怎样一步步生成、验证和收敛的

只看聊天结果，很容易以为策略是模型临场想出来的。仓库里的实现并不是这样。因子和策略都会先被压进受约束的规格对象，再交给可重复的计算流程验证。

因子先被压缩成明确的规格

研究计划中的候选因子和实验 variant 会被转成 FactorSpec。这个规格至少包含输入字段及其可用性滞后、参数、变换列表、验证计划、失败条件、成本敏感度和预期持有期。默认变换并不神秘，主要就是动量、均值回归、波动率、成交量惊奇、日内收益和针对加密市场的 carry 代理等几类。这里的 carry 代理，可以粗看成“用可观察到的市场结构去近似持有收益”的替代信号。

规格中会保留 availability_lag 和验证区间。这样系统在定义因子时，就把“这个信号何时可见”和“它在样本外还能不能站住”一起记下来，不用等回测结束再补解释。

因子不是只算一条数列，还要生成健康报告

FactorEngine 会产出因子序列、IC、RankIC、衰减曲线、样本内外统计、换手代理和一份健康报告。这里的 IC 和 RankIC，可以粗看成“因子值与后续收益是否同向、排序是否一致”的相关指标；样本内外统计则是在比较训练区和留出区是否一致。健康报告也不是装饰，它会专门做敏感性网格：改窗口、改平滑、改 winsor 阈值，再看指标变化多大。所谓 winsor 阈值，就是用来限制极端值对结果的扭曲。最后关心的是这个因子稳不稳，不只是某次回测好不好看。

如果同一个因子版本的工件已经存在，FactorEngine 会直接返回缓存结果。因子版本号既是缓存键，也是血缘键。

策略选择也不是自由创作

StrategyAgent 的提示词和回退逻辑都要求至少比较两个候选：RiskBudgetAllocator 和 EqualWeightAllocator。它会读取市场规则、回撤目标、因子健康报告、换手代理、样本外落差和仓位约束，再在这些条件下给出取舍。这里的策略生成，是在受限候选集合里做比较，不是自由发挥。

随后，流水线把选中的策略压成 StrategySpec，里面会写入再平衡频率、回看窗口、信号阈值、仓位配置、风险预算、最大仓位、熔断规则和失败 regime。回测请求再把因子版本、证据引用、策略决策、失败条件和 circuit breaker 一起带入回测引擎。

最后怎么收敛，靠的是比较。研究引擎会跑完整个实验矩阵，对每个 variant 保存 factor report、strategy decision、backtest request 和回测指标，然后按目标函数打分，从 Sharpe、收益、最大回撤、换手等维度选出最优实验。

健康报告不是附属物，它是策略选择之前的约束；回测也还不是终点，后面还要经过跨实验比较，才会产生“最佳结果”。

约束还体现在 DSL 层

工作台支持直接提交公式型因子，但公式 DSL 只允许少量白名单函数和简单算术，例如 ts_mean、ts_std、shift、rank、zscore、clip 和 winsorize。AST 校验会阻止任意语法进入执行器，所以这不是把 Python 代码随手丢给解释器。

7. 为什么系统里一定要有上下文锁定、预检查、审批和熔断

量化研究里常见的错误，不在算法本身，而在上下文偷偷漂移、市场规则被忽略，或者风险门禁被绕开。OpenFinance 在这些地方卡得很紧。

上下文锁定：先防止市场偷换

一旦计划创建完成，系统会把计划市场和各个 variant 市场都锁到同一个规范化市场值上。这样做是为了避免一个问题说的是 JP，某个实验 variant 却偷偷跑成 US。测试也覆盖了这种场景：先问 Nikkei，再说“给我一个低回撤策略并回测”，后续流水线会沿用 JP；如果你显式改说 US，才会覆盖掉会话记忆。

预检查：先看能不能迁移，再决定跑不跑

市场迁移预检查尤其重要。当前代码会对 CN 市场给出额外提示和阻断条件，例如 T+1、整手交易、交易时段覆盖、日内高成本因子风险和高换手不适配。如果 warning 达到阻断级别，流水线不会直接往下跑，除非你显式确认，或者允许系统根据市场规则做自动调整。

自动调整会直接改参数，例如降低换手、拉长窗口、切换再平衡频率、开启整手取整、调整预期持有期。preflight 在这里不是提示框，而是控制流上的闸门。

审批与熔断：谁能动，什么时候必须停

审批状态机被写得很清楚：requested → pending → approved → enabled → revoked/expired。不论是解锁 simulated live trading，还是调用高风险工具，都要经过这条链。更细的一点是，交易下单路由要求纸交易或模拟实盘订单至少带上 plan_id 或 evidence_pack_id，也就是一笔动作必须能追到研究来路。

TradingService 同时维护风险门、风险监控器和 kill switch。运行时失败条件如流动性枯竭、异常波动尖刺、拥挤度代理过高，会被评估成 warn 或 block；若风险监控器产生高严重度事件，系统还能自动打开 kill switch。

当前仓库的边界

这里所谓的“实盘”路径，实际上通过 SimBrokerAdapter 走的是模拟实盘流程，不是接到真实券商。审批、风控和熔断这些机制都在，但它们现在保护的是一个研究型、演练型执行环境。

8. 用一个完整例子，看懂一次请求如何走到最终结果

用一个仓库测试里真实覆盖过的例子最容易看清机制：先问一句“日经最近怎么样”，再接一句“给我一个低回撤策略并回测”。第二句里其实没有再写 JP，但系统还是会沿用 JP 上下文。

第一次消息：一般信息查询

系统把“日经最近怎么样”识别成 general info query，调用知识服务检索本地语料与外部 mock 来源，生成带引用的摘要，同时在会话记忆里写下 last_market=JP。这一步不会创建完整实验流水线，但会留下 reasoning 摘要和引用。

第二次消息：研究型请求

“给我一个低回撤策略并回测”被识别成 pipeline research。由于消息里没显式写市场，解析器会回看会话记忆，于是自动绑定到 JP。聊天接口立刻返回一个父任务 id，前端开始订阅后续事件。

生成计划与证据

研究引擎创建 plan_id，锁定市场为 JP，并把问题扩成研究计划。随后生成 evidence_pack_id，把来源列表和可信度评分写入证据库，同时在事件流里发出 artifact.created。

多视角 agent 接力

Buffett、Soros、Simons、Dalio、Kahneman、Factor 按顺序跑，每个都带着初始证据和反证线索产出结构化摘要。Kahneman 还会额外拉一轮反事实检索，用来下调过度自信的初始判断。

准备数据并跑实验矩阵

系统生成一份 JP 市场的 mock 数据集，得到 dataset_version。然后对计划里的多个 variant 逐个做因子计算、因子健康报告、策略选择和回测运行，每个 variant 都带着自己的 factor_version、strategy_version 和 run_id。

选最佳实验，并把结果挂回会话

系统按目标函数比较所有实验，选出最佳 run，生成最终报告，必要时再走一笔纸交易演练。完成后，会话记住这次的 last_run_id、last_plan_id 和 last_dataset_version，于是下一句“只把成本翻倍再跑一次”就有了明确起点。

9. 这套架构真正解决了什么问题，又在哪些地方仍然有限

它解决的是：答完以后还能不能接着做事

很多 AI 研究原型都能写出一个貌似合理的策略解释，但一旦你问“这结论用了哪份数据”“再跑一次时复用了什么”“如果换市场为什么被拦住”“这笔动作是谁批准的”，系统就接不上了。OpenFinance 主要补的，就是这块断点。

  • 自然语言请求会落成一串版本化对象，所以结果可以复跑、比较和恢复。
  • 多 agent 输出被压成统一结构，不同视角的分歧和共识都能进审计面。
  • reasoning 以用户安全的操作摘要呈现，可解释性和私有推理边界同时保留下来。
  • 风控、审批和熔断就在主流程里，不是回测后的附页。

它现在的限制也必须说清楚

  • 当前默认证据体系并不是实时互联网或真实终端数据，而是本地语料加 Mock 新闻、Mock 宏观源。
  • 当前数据集来自 MockDataFactory，所以回测是可复现实验，不是对真实交易历史的完整映射。
  • LLM 提供器默认允许 stub 模式，也就是在没有远程模型时退回到本地占位或模板化输出，因此系统仍能跑通流程，但“智能度”会明显退化。
  • SSE 事件总线是内存态的，实时回放窗口很短；真正长期保存的是审计和工件，而不是整条实时消息流。
  • 模拟实盘路径仍然是模拟，不应被误解为真实生产交易接入。
更合适的定位

把 OpenFinance 定位成一个可审计、可复现的研究与风控工作台，会比把它当成生产交易平台更准确。它已经把研究过程工程化了，但还没有越过真实市场基础设施那道门槛。

10. 读完前文后，你需要知道的几个关键词

下面这些词是 OpenFinance 的骨架词汇。理解它们，基本就理解了系统为什么能复用、能审计、也为什么有些地方必须阻断。

trace_id

一条执行链的总标识。计划、回测、审计事件和 trace 恢复都围着它转。

task_id / parent_task_id

运行时任务标识。前端任务树和后台异步执行靠它们串起来。

plan_id

研究计划编号。它把问题、实验矩阵、候选因子、候选策略和 agent 摘要固定下来。

evidence_pack_id

证据包编号。对应一组带可信度和时效评分的来源集合，可以被 agent、报告和 trace 恢复复用。

dataset_version

数据集版本号。由 schema、seed 和配置指纹化而来，用来保证“同一输入”有稳定身份。

factor_version

因子规格版本号。既是血缘键，也是缓存键，还能指回健康报告工件。

strategy_version

策略规格版本号。当前主要通过回测请求和报告持久化，而不是独立策略注册表。

variant

实验变体。表示同一研究目标下的一组具体参数组合，系统会把多个 variant 放进实验矩阵里并逐个比较。

run_id

一次回测运行的编号。对应最终报告、指标、订单、成交、持仓和成本拆分。

IC / RankIC

衡量因子是否和后续收益方向、排序关系一致的指标。它们不是最终收益本身，而是因子有效性的中间检验。

reasoning step

系统展示给用户和开发者的推理摘要单位，包含步骤类型、摘要、证据引用和置信度变化。

prompt_hash

提示模板的指纹，而不是提示词全文。它让你知道某一步来自哪一版模板，同时不暴露原始提示内容。

trace restore

把一条旧的执行链，按审计日志和注册表中的对象重新拼回可读上下文的恢复能力。

preflight

正式运行前的市场规则预检查。它不是提醒弹窗，而是可以真正阻断执行的闸门。

approval

高风险动作的审批状态链。保证“谁允许了什么”能被记录，而不是只看最终动作。

stub mode

没有远程模型时的占位运行模式。流程能继续跑，但输出会更接近模板或受限结果。

kill switch

风控熔断开关。既能人工打开，也能由高严重度风险事件自动触发。

OpenFinance 的价值，在于它把研究、验证、解释、审批和风险控制放进同一条可回溯链里。链条不断，结果就能复盘，前后动作也能对上。这时它更像一台研究工作台，而不只是一个会说话的 demo。
